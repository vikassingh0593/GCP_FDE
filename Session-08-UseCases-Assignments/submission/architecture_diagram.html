MedEvidence Architecture

MedEvidence answers HelixNova Medical Affairs questions about AX-17 from controlled documents and cites the page. It reuses the session 07 pipeline almost as-is and adds only what the brief requires: status, country and date filters, a lookup for exact IDs, a small adverse-event table, and an ADK agent built one tool at a time. It runs locally against project tredence-fde-1.

The one rule: Gemini may choose the tool, the wording and the relevance. Code decides which documents are allowed to answer. Status, country and effective date are SQL filters that run before the search.

Ingestion: files in, searchable chunks out

  • One parser to start. Layout Parser also accepts DOCX and runs OCR on scanned pages. We try it on all eight files first, look at the output, and add a second processor only if the scanned letters come out unreadable.
  • Session 07's built-in chunking to start. We open the chunks file and check three things: is Table 3 whole, is Table 14 whole, and how often does the repeated paragraph appear. We write our own chunking code only for what fails that check.
  • Registry fields copied onto every chunk. That way the search can filter with a simple WHERE status = … on one table.
  • MERGE instead of delete-and-recreate. Session 07's loader drops the table on every run. MERGE keyed on chunk_id lets you re-run a step, or add one new bulletin, without wiping anything.

Query: question in, cited answer out

  • Each tool owns its status rule. search_current allows only APPROVED documents in effect today. search_historical also allows SUPERSEDED ones. Session 06 hard-coded APPROVED, which makes the historical demo impossible.
  • IDs get an exact lookup. Embeddings blur identifiers, so if the question contains SB-AX17-2026-09 or HN-204, the tool filters to that document first.
  • The ranker cannot judge authority. The Ranking API doesn't know that v3.8 is superseded, so a simple sort in code runs after it. Putting the bulletin above the label is an assumption until the customer confirms it.
  • Citations are checked, not trusted. Gemini cites [chunk_id] as in session 07, and a few lines of code confirm that every ID it cites was in the evidence it received.

Agent architecture: one orchestrator, specialists only where a loop is needed

  • One orchestrator. The root agent decides the question's class and which tool to call, and is the only one that talks to the user. A specialist is called as a tool (ADK AgentTool), never "transferred to", so the orchestrator keeps the conversation (D68).
  • Functions where the steps must not vary. Search, lookup, comparison and escalation are fixed pipelines: the same filters and checks every time. An agent there would add an LLM hop (2–8 s), run-to-run variation, and a way to reword a checked answer.
  • A specialist where a loop is needed. sql_analyst writes a query, tries it, reads the error or an empty result, fixes it, and shows the last successful try. The fixed pipeline it replaces tried once and returned 0 rows for event = 'Rash' (D67).
  • Safety is code, inside the tools. try_sql and show_sql_result run every check themselves (SELECT only, curated views only, a BigQuery dry run of the real tables, byte and row caps). The agent can only try; it can never skip a check. Its steps are capped in code, and if it ends without a result, code says so.
  • Adding the next specialist follows the same five rules: the root stays the router, safety stays in code, results go through the relay, limits and evaluation cases come with it, and it is added only when a measured gap needs a loop.

What we keep, what waits

ItemDecisionWhy
One-command ingestionKeeprun_ingestion.py runs parse → tag → embed → load for every file in one go, and is safe to re-run. It's simple, and it's the piece we automate later.
Parse quality checkKeep, in Step 2.202_parse.py writes output/parse_report.json: pages in vs out, characters per page, empty pages, junk-character ratio, a known-phrase check and an OCR flag. A file that fails is quarantined, so Step 2.4 does not embed it. It catches empty or garbled text, but not a subtle misread such as "25" read as "75"; that needs OCR confidence scores or human review (see limitations).
Chunk boundariesKeep (decided in §4)Chunks end at sentence or paragraph boundaries and start with their heading path ("Dosage › Renal Impairment"). There is no fixed-token overlap: overlap mostly compensates for bad cuts, and it creates near-duplicates. Context comes from neighbor expansion at answer time instead. Only a paragraph longer than one chunk gets 1–2 sentences of overlap, and tables and warnings never overlap.
Chunk schemaKeep (decided in §5)The brief's 13 fields plus 15 more that earlier decisions need: dedup (content_hash, boilerplate, also_in), charts (block_type, generated), neighbors (position), version history (valid_to, raw_status), OCR (extraction) and lineage. Governance fields are copied from documents, which stays the source of truth.
Search routesKeep (decided in §6)An exact ID lookup for identifiers, because vector search never returns "nothing" and would summarize a lookalike when an ID such as HN-SAF-017 does not exist; the lookup can say "no such document". Hybrid search (vector + lexical) for everything else, because real questions mix exact tokens (AX-17, Germany) with meaning ("kidney" ≈ "renal"). Lexical alone floods with boilerplate, since "renal" is in every template paragraph.
Other search techniquesLater, each with a trigger (decided in §6)Query rewriting if a vocabulary-gap question fails. HyDE never (a made-up answer can invent a dose). Text-to-SQL: now adopted (row below). A knowledge graph if relationships multiply. Vertex AI Search as the managed "buy" alternative to discuss with the customer. Vertex AI Vector Search if latency or scale demands it. Start simple, measure, add only what a failure demands.
FreshnessDesigned, not deployed (your decision, D63; §7 has the blueprint)Bulletins take an event-driven path (Eventarc → the Cloud Run service ingest-one → Document AI → Vertex AI → BigQuery MERGE → verify; Cloud Run jobs handle the nightly batch and backfills), with retries, a dead-letter topic, a 5-minute reconcile sweep and an alert above 15 minutes. A nightly batch would be about 16 hours late while reporting "healthy". "Done" means a probe search through the bot's own code finds it. The automatic path comes after the agent works; the verify probe runs in run_ingestion.py now.
Scale (20×)Designed, not built (decided in §8)At 2.4 million chunks: a vector index with stored filter columns and a table clustered by product, country and status (cost per question); Top-K 50–100 and fuzzy duplicate detection (lookalike versions); batch and incremental-only ingestion (2.5 million pages); an embedding_model column with a blue/green switch for model changes (the provider retiring a version is the usual trigger), with documents arriving during the switch embedded by both models; a 50–100+ question evaluation set and per-user access control.
Vector indexBuilt but not needed yet (decided in §8)Our ~600–1,000 chunks are searched exactly; BigQuery uses brute force on small tables. 04_create_index.py keeps the production path ready. At 2–3 million chunks, exact search would scan ~18 GB per question, so production uses an index with the filter columns stored inside it. Because an index is approximate, its recall is measured against brute force on the evaluation questions (target ≥ 95–98%) before it is trusted.
Sources with linksKeep (your question, §7)Every answer ends with a Sources block built by code from the cited items: document ID, version, status, page or section, and a link that opens the original file at that page. The link needs Google sign-in and opens only if the user can read the bucket, so access is respected (no signed URLs, which open for anyone). In production it points to the official repository copy (discovery Q7).
Evidence cardsKeep (decided in §7)Code, not Gemini, writes a header for every evidence item: a short ID [E#], document, version, country, status, effective dates, a ROLE (LOCAL GUIDANCE / SUPPORTING EVIDENCE / HISTORICAL / STRUCTURED DATA), and the page, section and table. SQL rows get their own card, cited by view + record key + load time, with the document page preferred when the same number exists in a document. Conflicts are shown side by side with a CONFLICT note. Evidence is wrapped in <evidence> markers and treated as data, not instructions. Gemini cites [E#]; code maps it and checks it.
Top-K, Top-N and orderKeep (decided in §7)K = 20 candidates from BigQuery (a small K loses the exact table before the ranker sees it; a large K costs time and money but not answer quality). N = 5 after reranking, plus neighbors, is about 10–12 chunks, capped at ~6,000 tokens. Evidence is ordered by authority tier, then score. A 0.95 global study still goes last, labelled "supporting evidence, not German guidance". Score decides relevance; authority decides order and role.
Reranker roleKeep (decided in §7)The Ranking API decides only what is on topic. It cannot judge authority: v3.8's 50 mg table and the US table answer "renal dose?" as well as the current German Table 3. Status, country and dates are registry rules enforced in code. Because filtering happens first, of the brief's 20 candidates the 3 superseded and 2 wrong-country ones never exist, and the 5 overlap duplicates are never created.
Named things that don't existKeep (decided in §6)When a question names something specific (an ID, a table, a date, a country) and it does not exist, the bot says so and offers what does exist. "Table 7 in HN-204" gets "no Table 7; it has Table 14 and Table 18". "US guidance before March 2026" gets "the only US label took effect 1 Aug 2026". Similarity search never silently substitutes the nearest match, and an empty result is often the correct answer.
Open questionsKeep (your requirement, §6)Users can ask anything, so the agent routes by question class: guidance (search), a specific document (lookup), numbers and metadata (text-to-SQL), mixed (both), unclear (ask back), patient-specific (escalate), small talk (no tool), not in the data ("I don't have this in the controlled documents", plus what is covered). It never answers from Gemini's own medical knowledge: an answer without valid citations is blocked in code.
Collection catalogue (D46)Your idea in Step 5b"What is AX-17?", "What documents do you have?" and vague requests ("show for usa") are answered by the agent without a tool, only from a catalogue built by code at start-up from the registry and the stored tables (documents, countries, versions, dates, table titles). It never describes what the medicine is or treats: the documents don't say, and Gemini would invent it. Vague requests are never sent to search.
No hard-coding (D47)Your question in Step 5bProduct names come from the registry (several products → "Which product?"); document-ID shapes are learned from the real IDs; hand-off contacts and document-type rules sit in policy.py; the assistant is named MedEvidence in env.sh. A renamed PDF or a new document needs only a registry row and an ingestion run.
Grounding check (D66)Built after user testing (your call: production tools only)Every answer Gemini writes is checked claim by claim against its own evidence by the Vertex AI Check Grounding API; below 0.6 support it is blocked. It replaced a hand-made word list that refused correct questions five times, and it catches the Step 4 wrong-column error that the number check cannot (support 0.48 → blocked).
SQL specialist agent (D67)Built after user testing (your decision)sql_analyst: an ADK AgentTool that writes, tries and repairs SQL; its tools are code and re-check everything; at most 4 tries and one result; rows shown word for word. Found in live testing and fixed: the agent retyped a long query with a typo, so the result tool now shows the last successful try instead of new text.
Agent pattern (D68)Your directionThe first agent stays the orchestrator and router; specialist agents are added on top of functions only where a measured gap needs a reasoning loop, each as a tool, with safety in code, results through the relay, code limits and its own evaluation cases.
Model change (D69)External review (your choice: lowest cost)Gemini 2.5 Flash retires on Vertex AI on 20 Oct 2026. The cheapest replacement, 3.1 Flash-Lite, routes perfectly, but as the answer writer it sometimes thought for two minutes and wrote claims the grounding check could not verify (31 of 33, p95 152 s). Patient check, two signals (D70)External review (your go-ahead)The word patterns missed 5 of 8 reworded patient questions (indirect wording, a typo, German, shorthand). Either signal, "unsure", or a failed call sends it to a person; nothing can undo that. Trial: 22 of 22 right, including French and Spanish.
Small talk (D45)Your decision in Step 5b (widened, like session 06's general-conversation lane)Greetings, "how are you?", "what can you do?", help with phrasing and light non-medical chat are answered by the agent without a tool. Medical content from its own knowledge (another drug's dose, "what is eGFR?") is declined. Code check: a no-tool reply containing a dose or clinical figure ("400 mg", "12.7 %", "3x ULN") is replaced by a fixed message, because such numbers may only come from a checked tool answer. A medical statement without a number is stopped only by the instruction until Step 7.
Extension: MCPFuture (your question)New outside tools (e.g. the document repository or a safety database) plug in as MCP tools through ADK's McpToolset, and the root agent routes to them like its own tools. Because their code is not ours: an allowlist, read-only with human approval for actions, output treated as untrusted evidence cards, and the same citation, number and sufficiency checks.
Agent shapeKeep (decided in §11)The agent earns its place by making decisions a fixed pipeline cannot: current vs historical, splitting a comparison per study, analytics via SQL, asking back, escalating, follow-ups. Its costs (an extra model call, a possible wrong tool) are contained because the safety rules live inside the tools and routing accuracy is measured. One root agent with six tools; no sub-agents. Each retrieval path is a fixed pipeline wrapped as a tool, so it runs the same way every time. The agent understands the question (class, tool, current vs historical, country, date and IDs it extracts), and code validates what it extracted. It never decides status, entitlement or legal effect: those are registry facts enforced in code. escalate hands off to a person at Medical Information.
Sufficiency gate and patient boundaryKeep (decided in §10)"Enough evidence?" is decided from several signals, never one score: the question's key terms appear in the cards, the required local guidance exists, and Gemini's checked yes / partial / no verdict. Scores are not calibrated, and templates can score high. A question about one patient's treatment is never answered as a decision: the bot shows the general label reference, flags the bulletin's review trigger, and routes to Medical Information, enforced by the instruction plus a code pre-check.
Injection and inference guardsKeep (decided in §10)Planted instructions: evidence is data inside markers (prompt), filters and tools live in code (answer time), and an injection scan at ingestion quarantines instruction-like text. The scan is needed because a planted "100 mg" would otherwise pass the citation check. Inference: no dose or number is ever calculated; a number check blocks any figure that is not in a cited card, and a user's wrong premise is corrected from the evidence.
EvaluationKeep, in Step 8 (from session 04 pattern 24 and session 03)Retrieval and generation are scored separately, so a wrong answer is traced to the stage that broke (never retrieved, ranked too low, reasoning failed, citation wrong) and we fix the right thing instead of swapping the model. The set includes adversarial questions for prompt injection and filter bypass. It is re-run after every change.
Text-to-SQLKeep, in Step 6 (your decision, §6)The "structured" branch of the session 04 production pattern. Verified queries come first (compare_studies keeps its fixed SQL, so demo 4 stays reliable). Governed text_to_sql (session 09 guardrails: SELECT only, dry run with a cost cap, 100 rows, one repair, SQL shown) handles new analytical questions over curated views only: v_adverse_events (one row per study + event, so no AVG/SUM over the 4 repeated subgroup rows) and v_documents. Never the chunks table. SQL answers numbers and metadata, never "current guidance", and every document row states its status. Guardrails stop dangerous SQL, not wrong SQL.
Hard filters vs rankingKeep (decided in §5)Hard filters run in SQL before the search: product, country (GLOBAL studies let in but labelled), status set by the tool, in effect now or on the asked date, and no boilerplate. Ranking only orders valid evidence: relevance, authority (bulletin › label › study), then recency. Filtering after the search could leave nothing valid in the top 20.
Duplicate controlKeep (decided in §4)Exact copies (the bulletin table ×3) are hashed and kept once per document, with their other locations recorded. Copies are never merged across documents, because v3.8 and v4.2 carry different status. Template paragraphs (90–99 per file) are found by masking numbers and are tagged boilerplate: kept for audit, never deleted, and excluded from search so a "16.2%" decoy never reaches Gemini.
Parent-child retrievalNot now (decided in §4)Cleaner in theory: search small children, read the whole parent section. On our data the parent section is mostly template paragraphs with decoy numbers, so Gemini would get the real dose surrounded by decoys. It also needs a second chunk level in custom code. Neighbor expansion (same section, skipping boilerplate) gives the context more cheaply. Parent-child is the production upgrade for real long clinical reports.
Chunk size by content typeKeep (decided in §4)Layout Parser tags each block's type automatically, and the type sets the rule. A table is one chunk at whatever size it is. Warnings and the bulletin header block stay whole. Narrative is grouped up to a 512-token ceiling, never crossing a heading. The ceiling is tested (512 vs 256), not copied from the lab. Only that one number is configured; every other size follows from the document's own structure, and the Step 2.2 checks verify it.
Verbatim answersBuilt in Step 4 (D31)The agent never adds to or rewords an answer: the tool stores its checked answer and Sources, and an after_model_callback shows exactly that text, discarding the model's own wording. The citation and number checks ran on that text, so a rewrite could change a number after the checks passed. Enforced in code, not only in the prompt. Anything added must be fixed code-built text (e.g. a jurisdiction note when a follow-up changes country) or a new answer that passes the same checks. No disclaimer footer until HelixNova provides approved wording (A11).
Local hosting onlyYour decisionThe agent runs on the laptop in adk web and is never deployed to GCP. Google Cloud is used for the data and model services only (BigQuery, Document AI, Vertex AI, Ranking API).
Offline testingBuilt (your question, before Step 4)Record and replay: real responses from embeddings, search, ranking and Gemini are recorded once (MEDEVIDENCE_RECORD=1) and replayed with MEDEVIDENCE_OFFLINE=1, where the runtime refuses to create any Google client. 8 offline tests run in about 3 seconds with no cost and no 429s; fixtures are re-recorded when the corpus, filters, prompts or models change. A query-embedding cache keyed by model avoids repeat calls during development.
Health monitoringKeep (your requirement)Ingestion checks and every agent question are logged to BigQuery (pipeline_health, agent_log), and the golden set runs nightly, so problems show as trends with thresholds rather than as one printout. Every AI output is checked against a deterministic reference. Built here: the tables, the logging and a health report. Production: a Looker Studio dashboard and Cloud Monitoring alerts.
Testing AI outputKeep (your question)Every model output is checked against something deterministic, never against another model: parser text against the PDF's own text layer (how "OD → QD" was caught), answers' numbers against the evidence, demo answers against the known-answer set. Each manual catch becomes an automatic test in tests/. Risky spots: numbers, units, abbreviations, negations, dates and time zones, and which column a value sits in.
Faithfulness checkBuilt in Step 2.2 (new finding)Every native PDF's parsed words are compared with the PDF's own text layer.
